## 累计误报率（截至 2026-11-10，统计自 `reports/health-tickets/`）

**裁决（2026-11-10，用户）**：巡检照常跑；观察期未满一周，**误报率只做记录，不动阈值、
不动告警**。

统计口径：工单目录里 `evidence.notes` 命中 `rule1c` 的全部工单（rule1c = 最近一次可比成功
的行数低于 `min_rows_per_run`），逐张看 `terminal` 与 `lifecycle` 里的人工判定。

| 指标 | 值 |
|---|---|
| rule1c 工单累计 | **3 张**（`boxofficemojo` / `cisa` / `gb-standards`） |
| 其中 `terminal: closed`（误报关闭） | **3 张** |
| **工单级误报率** | **100%（3/3）** |
| rule1c 占全部工单 | 3.3%（3/90） |
| 源级：出过 rule1c 的已声明源 | **8.3%（3/36）** |
| 有效观察期 | **< 1 天**（首轮判定 2026-11-10 06:30 CST） |
| 该批之后新建工单 | 1 张（`20261110-eastmoney-disclosure-plan`），其中 rule1c **0 张** |

**这 100% 不能读成「阈值不准」**，理由三条，缺一不可：

1. **分母是 3，且同因**：三张单来自同一时刻、同一条件（见上文 11-06 批量探针），
   不是三次独立抽样，方差无意义；
2. **它们是 rule1c 的**首轮**判定**——上线后第一次拿历史数据比对，天然会撞上那个
   探针尾巴；该批之后的后续运行没有再出 rule1c 单（其后新建的唯一一张工单是
   `20261110-eastmoney-disclosure-plan`，与行数下限无关）；
3. 三个源已暂撤声明（11-12 / 11-15 / 11-17 恢复），期间的"0 误报"只说明**没在判**，
   不说明阈值稳。

所以按裁决只记录、不调参。观察期满（≥ 2026-11-17 且三源都已恢复重跑）再算第二次。

## 一周后怎么判

1. 跑 `python3 scripts/min_rows_false_positive_report.py --days 7 --from-pg`；
2. 看每个源「最后一张单之后是否又达标」——**>0 不等于误报**（可能真低产后修复，或上游恢复）；
3. 只有「出单 → 立即恢复 → 再出单」这种反复，才是阈值太敏感的实证；
4. 误报率 >20% 的源回退：删掉 manifest 里的 `min_rows_per_run` 行，再跑
   `python3 scripts/validate_manifests.py` 复核。

贴边项优先看：`eastmoney-data` 2/2、`eastmoney-futures` 1/1、`fangchan-market` 79/79。
