## 一、结论

**不点亮**（不加 `schedule:`），并把窗口缺省值从「上个完整自然月」改成**滚动 6 个月**。
理由不是保守，而是原设计会在上游回填期内把偏低的数**永久固化**。

## 二、证据：上游回填滞后（同月对比，排除季节性）

用同一个 API 的计数端点按月取合同数（`award_type_codes=A,B,C,D`，2026-11-11 实测）：

| 月份 | contracts | 相对 2025-10 的比例 |
|---|---|---|
| 2025-10 | 651,682 | 100% |
| 2026-05 | 654,069 | 100% |
| 2026-06 | 580,577 | 89% |
| 2026-07 | 484,021 | 74% |
| 2026-08 | 218,111 | 33% |
| 2026-09 | 240,896 | 37% |
| **2026-10** | **100,757** | **15%** |

同是 10 月：2025 年 651k vs 2026 年 100k —— **不是季节性，是滞后**。越近的月份越不全。

## 三、为什么原设计会固化错误的数（机制，不是猜测）

1. 原缺省窗口 = **只取上一个完整自然月**。
2. 落库形态是 `crawl_items (run_id, idx, payload)`——**每次运行一份追加快照**，
   消费侧取最新 run。所以「重取」本可以纠正历史。
3. 但每月一次的调度里，每个月只在**它刚过去的那个月**被抓过一次（此时约 15% 完整度），
   之后不再进入任何窗口 → 那个月的 15% 就是它在这条线上的最终值。
4. 结果：序列整体系统性偏低，且**没有任何一处会报错**（行数正常、字段齐全、200 正常）。

这正是本仓反复出现的「未知被当成已知」：缺陷不在取数失败，而在**取到的数看起来是完整的**。

## 五、点亮（补 schedule）的解锁条件

满足全部三条再补 `schedule`，缺一条都不要点：

1. **窗口已覆盖滞后期**——已满足（滚动 6 个月；实测 6 个月前的月份仍在 74%~100%，
   会被后续运行继续抬高并收敛）。
2. **首爬验证过一次真实调度**：deploy 后手动触发（Console「立即触发」或 `platform_trigger`），
   确认 `crawl_runs` 有成功记录、`crawl_items` 行数非零、`metrics.window_start/window_end`
   落在滚动 12 整月内。**判据看 run 记录，不看 Console 的绿点**。
3. **明确「部分和」对外口径**——**已满足（2026-11-11 结构化解法，不靠文档提醒）**：
   原先只有 README 一句"部分和"，读者无法分辨"这组是全部"还是"这组只看到头部"。
   现补两列，把口径变成可计算的事实：
   - `page_cap_reached`（bool）：该 (类型, 月) 批次是否被页数上限截断。实测几乎恒 `true`
     （每月每类远超 300 笔），故**默认就该按样本读**；
   - `batch_total_awards`（int|null）：同 filters 下 `/search/spending_by_award_count/`
     返回的**全量笔数**，作分母。`null` = 未知（计数调用失败），**不是 0**。
   实测（2026-10, 类型 A）：采样 297 / 全量 35,031 = **笔数覆盖率 0.85%**。
   样本按金额降序，**金额覆盖率必然更高，但没测过所以不写数字**。
   README 增「口径：这是头部样本，不是全量」一节，明确"看趋势不看绝对量、
   对外一律称头部样本和"。

   > 副作用（已实测）：每个 (类型, 月) 多一次计数请求 → 6 个月 × 4 类 = +24 次，
   > 整轮 72 → 96 次，`run(limit=3)` 实测 **136.3s → 164.5s**。月频可接受。
