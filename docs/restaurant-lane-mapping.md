## 2. 日股 3.4 — EDINET key 闸门（实测，非猜测）

```
GET https://api.edinet-fsa.go.jp/api/v2/documents.json?date=2026-11-06&type=2
→ HTTP 200 {"StatusCode": 401, "message": "Access denied due to invalid subscription key..."}
```

结论：EDINET API v2 **必须有 subscription key**，无 key 时所有端点一律 401。申请通道 =
面向 `data-sources@` 域邮箱的邮件申请（日本金融厅），需人工提交并等待下发，**不是代码问题**。

因此任务 3.4 按任务书自身的条款**如实挂起**：「key 未到位时任务如实挂起不阻塞他波」。
挂起处置：
- 不建半成品单元（不留无 manifest 的目录，避免污染 conformance gate）；
- 日股 4 家在板面上一律显示「不可得：EDINET key 未到位」，不显示空序列；
- key 到位后按本文件 §1 的车道位接 4 家（泉盛 7550.T / 萨莉亚 7581.T / 日本麦当劳 2702.T / 云雀 3197.T）。

## 3. A股 3.6 — 经营公告口径的实况（重要，需裁）

任务书验证条件是「6 家 A股**最新经营公告事件**经既有供给可查」。实测结论：**该口径对餐饮
A股不成立**，不是抓取失败：

| 证据 | 结果 |
|---|---|
| `cninfo-operating` 既有库内 payload（run 2026-11-06 批次） | 200 条，汽车/钢铁/建材等产销快报；6 家命中 **0** |
| 追加定向 run（2026-06-01..2026-11-08，五类关键词齐全，`page_size=100`） | 114 条新抓，累计 **214 条 / 105 家公司**；6 家命中 **0** |
| 关键词定向 run（`keyword=经营数据`，2026 全年） | 0 行（上游无该标题族） |

原因（业务事实，非技术缺陷）：餐饮 A股 不发布「产销快报 / 销售简报 / 发电量 / 主要运营数据 /
经营简报」这类**月度经营数据**公告，披露节奏是季报/半年报/年报。

**替代供给（2026-11-08 二次实测，含两次自我更正）**：

> **二次更正（2026-11-08 当晚）**：初版写「6 家均有营收/净利」但依据错（那是实体全部概念
> 观测总数）；第一次更正写「只有全聚德/西安饮食有」，**仍然是错的** —— 因为只按宇宙登记的
> **裸 6 位码实体**查。实际这 4 家的财务观测落在 crawler 另建的**别名实体**上
> （`603043#8227` 一类：公司被风险警示/改名后以新名字重新注册了一个实体）。按「同基础代码 +
> 归一名字（剥 `ST`/`*ST`）」合并后，**6 家全部有营收/营业利润/净利，各 25~47 期，均到 2026-09-30**。

| 公司 | 宇宙裸码实体 | 财务观测实际所在实体 | 营收/营业利润/净利 | 最新期末 |
|---|---|---|---|---|

> 供源为 `akshare`（东方财富财务数据转载），不是 `cnreport`——该 6 家在 `cnreport` 下 0 条。
> 全库共有 40+ 条 `code#id` 别名实体（普遍发生在 ST/改名公司），**任何按裸码解析实体的下游
> 都会漏数据**；已把该形状作为跨线缺陷记录（见 `tasks.md` 6.4 挂账）。

**读路径已修（2026-11-08）**：这两个下游原先不同步——看板
（`dashboards/build_restaurant_company_spec.py::_sibling_ids`）早按「同基础代码 + 归一名字（剥
`ST`/`*ST`）」取数，而 MCP 工具 `restaurant_company_financials` 只按裸码实体查，于是对
广州酒家/ST绝味/紫燕食品/巴比食品 4 家返回「源侧未覆盖，不插值不补零」——**库里有、报成源侧
没有，比空数组更坏**；`restaurant_universe` 同因把这 4 家的车道标成 `no_data`。
现 `restaurant_tools.py` 按看板同一规则修好：判据=**同 6 位基础代码 + 同 `entity_type`**
（名字只作披露，不作准入闸——改名公司 `603007 → 顺景科技` 归一名字也对不上，坚持名字相等就
永远读不到）；裸码实体优先，否则取数据最全的同码兄弟实体（同一概念不跨实体拼接，绝不跨公司
借数），输出用 `observations_from` 明示取自哪家；宇宙清单的计数 SQL 改按
`split_part(code,'#',1)` 圈定并合并别名计数。
实测 6/6 A股三概念各有 20 期至 2026-09-30；56 条测试绿，五条反向验证
（关掉兜底 / 兄弟不限基础代码 / 恢复严格名字闸 / 计数退回裸码 id 过滤 / 改坏归因文案）分别精准转红。

即：**经营公告车道对餐饮宇宙无供给**（业务事实：餐饮 A股 不发布月度经营数据公告，披露节奏是
季报/半年报/年报），而**财务报表车道覆盖 6/6**（营收/营业利润/净利，均到 2026-09-30）。
所以 3.6 的「零新建 A股爬虫」这一核心要求成立（本单确实没有新增 A股单元），但验证句里的
「经营公告事件」应改为「季度财务报表事件（akshare 既有车道）+ 行情」。

**处置**：不勾 3.6，留待裁——是接受「财务报表替代经营公告」这一口径改写，还是另立「餐饮 A股
季报事件面」子任务。**注意「利润表只覆盖 2/6」的说法已作废**：那是读路径不解析 `code#id` 别名
实体的假象（见上文「读路径已修」），实测 6/6 都有营收/营业利润/净利，各 20 期至 2026-09-30。
二者都不影响其它波次。
